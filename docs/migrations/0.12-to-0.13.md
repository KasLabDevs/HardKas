# Migration Guide: 0.12.0-rc.29 to 0.13.0-rc.1

What changes for a project that used `0.12.0-rc.29`, in the order you are likely to hit it. The full list is in
`CHANGELOG.md` at the repository root.

## 1. Node.js 24.22.1, exactly

`@hardkas/cli`, `@hardkas/core`, `@hardkas/testing`, `@hardkas/pskt-native` and the monorepo root declare
`engines.node: "24.22.1"`. `hardkas doctor` passes on 24.22.1, warns on another 24.x and fails on any other major line.
Install Node.js 24.22.1. Documents that said "22.5 or newer" or "Node 18" were wrong.

## 2. Artifacts: hash version 5

New artifacts carry `hashVersion: 5`. Artifacts with hash version 4 or lower are still read, with the `LEGACY`
authentication scope. A replay verdict, or any other decision path, refuses that scope with `REPLAY_LEGACY_AUTH_SCOPE`.
Re-issue the artifacts you still decide on:

```bash
hardkas artifact migrate path/to/artifact.json --to 5
```

`docs/reference/artifact-schema.md` shows the version 5 shape.

## 3. The dashboard and `dev-server` commands are gone

`apps/dashboard`, its Express server, the `runDashboard` export of `@hardkas/cli/public` and the `express` dependency of
`@hardkas/cli` were removed. The CLI no longer registers the `dev-server` command group. For the local HTTP/SSE
surface, use `@hardkas/dev-server` from code.

## 4. Covenants: the v1 engine

Covenant work moves to transaction v1 and the engine:

```bash
hardkas silver covenant genesis <record>
hardkas silver covenant transition <covenant-record>
hardkas silver engine plan <operation> <spec>
```

The SDK equivalent is `hardkas.covenants` (`planGenesis`, `planTransition`, `planContractDeploy`,
`planContractSpend`). `planDeploy()` and `planSpend()` still refuse with `COVENANT_PLAN_UNSUPPORTED`. Payments, batches
and consolidations stay transaction v0 unless you ask for v1 (`--tx-version 1`). Only 1:1 auth-bound transitions have
real-node evidence. The other topologies pass the engine's own checks only, so test them on simnet before you rely on
them.

## 5. `@hardkas/testing`: covenant matchers want node evidence

`toPassCovenantTransition()` now defaults to `minEvidence: "CONSENSUS_SIMNET"`. `toPreserveCovenantId()` and
`toProduceSuccessor()` fail with "NOT VERIFIED" when the result was not checked by a node. Below that level the
successors are the testbed's own ledger writes. Suites that run with the SilverScript runner (`SCRIPT_VM`) and want to
keep that level must say so:

```ts
expect(result).toPassCovenantTransition({ minEvidence: "SCRIPT_VM" });
expect(result).toPreserveCovenantId(genesis.covenantId, { minEvidence: "SCRIPT_VM" });
expect(result).toProduceSuccessor(1, { minEvidence: "SCRIPT_VM" });
```

## 6. L2 is an extension

The L2 commands, the Igra profiles and the Foundry/solc toolchains come with the `l2` extension (not published in this
release, see below):

```bash
hardkas extension install l2
```

`@hardkas/ext-l2` is not published in this release, and neither is `@hardkas/l2`, so this works only from a local build or tarballs. An L2 mainnet write needs
`allowMainnet: true` (SDK) or `--allow-mainnet` (CLI). This differs from Kaspa L1, where mainnet broadcast is blocked
with no flag.

## 7. The simulator is experimental

`@hardkas/simulator` (and its `kaspa-simulator` bin) is new in this line. It is an approximate model and its verdicts are
not consensus evidence. Read the list of known divergences in `docs/status/limitations.md` before you trust a timelock,
covenant or mass result from it. Confirm such results on simnet.

## 8. Merchant compatibility battery

`scripts/run-merchant-compatibility-battery.mjs` (v1) no longer runs. Use
`scripts/run-merchant-compatibility-battery-v2.mjs`. It writes each run to its own directory (default
`.hardkas/merchant-compat/<runId>`) and only records PASS for operations it executed. The results committed before
this release are not evidence (`logs/README.md`).

## 9. Fees and sending

The default fee no longer overpays: the relay minimum (100 sompi/gram) is charged on the larger of the compute mass and
the normalized transient mass, as rusty-kaspa v2.1.0 does, so plan hashes change. A plan, signature or send above 0.1 KAS of
fee is refused with `FEE_EXCEEDS_MAX` unless you raise the ceiling (`maxFeeSompi`, `--max-fee`, or
`networks[<net>].maxFeeSompi`); a node fee rate above 10,000 sompi/gram is refused with `FEE_RATE_ABOVE_BOUND`.
`tx.send` needs the signed transaction's plan (`SEND_PLAN_UNRESOLVED`, `SEND_PARENT_NOT_PLAN`, `SEND_PLAN_UNREADABLE`);
`allowUnplannedSignedTransaction` (CLI `tx send --allow-unplanned`) is the explicit exception and skips the plan's fee
check.

## 10. Keystores 2.1.0

New keystores authenticate their `network` and `address` and bound the KDF parameters. 2.0.0 keystores are still read,
but a keystore written by this release cannot be opened by an older HardKAS.

## 11. Simulator scripts and identity

Simulator scripts follow Kaspa semantics: the Bitcoin pattern `<t> CLTV DROP …` fails (the operand must be consumed),
clean stack and push-only signature scripts are enforced, and an invented genesis covenant id is rejected (compute it
with `kaspaCovenantId`). The simulator identifies itself as `2.1.0-kaspa-simulator`, listens on 19110 by default, and
`HARDKAS_SIMULATOR` / `HARDKAS_ALLOW_SIMULATOR_NODE` have no effect any more.

## 12. ZK (experimental)

- `verify-math` / `verifyZkProofMath` return `ZK_GROTH16_MATH_VERIFIED` only for an anchored verification key: pass
  `--expect-vk-hash <fingerprint>` (`expectedVerificationKeyHash`), taken from a source you trust. Without it a passing
  pairing is `ZK_GROTH16_MATH_VALID_UNANCHORED_VK` (exit 1). Renamed values: `FIXTURE_COHERENCE` →
  `FIXTURE_COHERENCE_SELF_ATTESTED`, `…_FIXTURE_BOUND` / `…_MATH_ONLY` → `…_PINNED_VK` / `…_UNANCHORED_VK`.
- RISC Zero receipts are verified with `hardkas zk toccata verify-receipt` (`verifyR0Groth16ReceiptLocal`); the
  `mathVerified` flag of `buildR0Groth16Transaction` is ignored.
- `build-scripts` locks are `IMAGE_ID_ONLY` by default (anyone with a valid receipt spends). `--mode
  proof-and-output-bound` (`bindingPolicy`) builds an `IMAGE_ID_AND_OUTPUTS` lock: fund it with `requiredFundingSompi`.
  `utxoBinding` / `--utxo-txid` / `--utxo-index` are refused (`ZK_UTXO_BINDING_UNSATISFIABLE`).
- The opcode is `0xa6`; a RISC Zero spend needs a compute budget of at least 1550 (default 1600).

## 13. CLI exit codes

- `hardkas doctor` exits 1 when any check in its report fails (warnings and skips keep 0). Read `summary.failed` or the
  exit code; the report is unchanged.
- `hardkas init` over an existing project answers `PROJECT_ALREADY_INITIALIZED` (exit 1), not `UNKNOWN_ERROR`; `--force`
  still overwrites `hardkas.config.ts`.

## 14. Installing from npm

`0.13.0-rc.1` is not on the registry yet. A project that `hardkas init` scaffolds pins `@hardkas/*` to the exact CLI
version, so `npm install` in it fails until every package of the release is published. Until then, install from
tarballs.
