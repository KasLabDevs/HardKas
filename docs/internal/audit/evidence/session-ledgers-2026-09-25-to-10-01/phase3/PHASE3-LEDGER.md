## CORRECTION (2026-09-29, after the report; found while designing the adapter) — the R' claim was false
- Source (debugger/cli/src/main.rs + session.rs): the runner executes `DebugSession::full(active_sigscript, active_lockscript)` = ITS OWN encoding of `args` (silverscript-abi) followed by ITS OWN compiled bytecode. An input's `signature_script_hex` only goes into the tx context; it is never executed, and no P2SH hash check is made.
- Probe (probe-explicit-sigscript/, Guess(42)): args 42 + HardKAS unlock for 41 → PASS; args 41 + HardKAS unlock for 42 → FAIL "guess = 41"; args 42 + garbage sigscript `00` → PASS; args 42 + unlock 42 → PASS. Output kept in probe-explicit-sigscript/out.txt.
- So R' = R by construction: "runner accepts HardKAS-built unlock scripts 19/19" is RETRACTED (it proved nothing about HardKAS's unlocks). Likewise "redeem of another contract / non-push-only → runner ACCEPT" means the runner never looked at those unlocks, not that it accepted them after executing them.
- Still valid: runner 24/24 (its own encoding); simulator 0/15; node verdicts. The signature binding holds and is now controlled (sig-binding.mjs → sig-work/): HardKAS signature over the scenario tx with silverc's P2SH lock → PASS, over another instance's lock → FAIL, for tx versions 0 and 1. A signed PASS therefore proves silverc bytecode == the runner's compile.
- Consequence: HardKAS's unlock construction (encodeSilverEntryArgs + silverUnlockScript) is validated only by the node (corpus e2e), never by the runner. The adapter must not pass unlock scripts to the runner or claim it tests them.
- Upstream already knows: kaspanet/silverscript #253 (open, 2026-09-14) reports exactly this ("cli-debugger silently ignores tx.inputs[active_input_index].signature_script_hex in test-file mode").
