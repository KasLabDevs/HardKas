# HardKAS 0.13.0-rc.3 — release notes

**Status: published on npm.** `latest` and `next` are `0.13.0-rc.3` (22 packages, tag `v0.13.0-rc.3`). The [CHANGELOG](../../CHANGELOG.md) has the full list.

This candidate closes the gaps between what the SDK could do and what the CLI offered, and adds what neither had. Every capability below runs end to end on an isolated rusty-kaspad 2.1.0 node (simnet), refuses mainnet before any key is read or any connection is opened, and reaches a public testnet only behind the payments opt-in.

## What is new

- **ZK spends through HardKAS's send:** `hardkas zk toccata spend` and `zk toccata observe` (SDK `spendR0Groth16Lock`). A RISC Zero Groth16 lock is spent through `sdk.tx.send`, recorded like any other send. The node verifies the proof: HardKAS claims no on-chain ZK verification of its own.
- **Escrow outside the dev server:** `sdk.escrow` and the `hardkas escrow` lifecycle commands (`create`, `fund`, `status`, `prepare`, `sign`, `release`, `reconcile`), with signers in separate workspaces. The dev server uses the same module; its HTTP API is unchanged.
- **Covenants and tokens from the CLI:** `silver covenant start|advance` (1:N, N:M, termination) and KCC-20 tokens (`sdk.kcc20`, `kcc20 deploy|transfer|balance`, experimental).
- **Absolute lock times (CLTV):** `--lock-time-daa` / `--lock-time-ms` on payments, SilverScript spends and covenant transitions; a transaction is never sent before the node passes its lock.
- **Spends from ECDSA addresses:** `accounts real generate|import --ecdsa`.
- **Recoverable HD wallets** (experimental): the `hardkas wallet hd` commands, a BIP39 phrase and Kaspa's derivation, spending across all the wallet's addresses.
- **Browser wallets sign, HardKAS checks** (experimental): KasWare, Kastle and Kaspire through `@hardkas/sdk/client`, and a probe page to check a real wallet ([browser wallets](../start/browser-wallets.md)). The real extensions are unverified until that probe is run.
- **The history of an address:** `hardkas history`, and `artifact verify|tx status --address` for transactions whose outputs were spent since.
- **Watch an address:** `hardkas watch <address>`.
- **Several recipients in one transaction:** `sdk.tx.plan({ outputs })`, `tx plan --to <recipient>=<kas>` (repeatable) and `tx batch --one-transaction`: one output per recipient, one change output, one fee, one submission. More recipients than fit in one standard transaction (about 193) are refused before signing, with how many fit. Without the flag, `tx batch` still sends one transaction per payment.
- **SilverScript tests judged by a node** (experimental): `hardkas silver test --on-node` runs each case as the real transaction it describes and records the node's verdict (`CONSENSUS_SIMNET` on simnet) with the txid; a case no real transaction reproduces is reported as such, never as a pass. The runner mode is unchanged and its runner stays UNVERIFIED.
- **Escrow releases of large amounts:** a release to one large output (such as 5 KAS) was refused before it was sent; it now goes out.
- **Single-command payment send + wait:** `hardkas tx send --wait` (with `--wait-timeout`, default 60 s; exits 1 with `TX_SEND_WAIT_FAILED` and `outcome: submitted` on timeout) and `hardkas tx wait --url <ws://...>` allow sending and confirming on any node without a `hardkas.config.*` file.
- **Agent-oriented quick recipes & AI docs:** `hardkas --help` surfaces the core recipes directly before `Usage:`, alongside `https://hardkas.dev/llms.txt`, `llms-full.txt`, and `docs/ai/`.
- **Dependencies and fixes:** zod 4.6.7 (GHSA-mrhx-c7xc-m3w5), with what HardKAS accepts unchanged; `tx batch` no longer fails a payment when the node accepts the earlier ones mid-batch, and refuses mainnet before it opens any keystore; the RPC ports in the documentation agree with what the managed localnet publishes (16210, 17210, 18210).

## Install

```bash
npm install --save-dev @hardkas/cli@0.13.0-rc.3
npm install @hardkas/sdk@0.13.0-rc.3
```

Use the exact version.
