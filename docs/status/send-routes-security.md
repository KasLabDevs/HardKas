# Send routes: what each one checks before a broadcast

HardKAS has several public ways to put a transaction on a Kaspa L1 network. They do not all check the same things before the broadcast. This page lists every route that ends in a node's `submitTransaction`, side by side.

Three rules hold for every route:

- **Mainnet is locked down: no route reaches a mainnet node at all, reads included** (MAINNET TOTAL LOCKDOWN, owner decision 2026-11-09). A mainnet network, under any spelling or behind any alias that declares it, gets no endpoint and no connection (`MAINNET_CONNECTION_DISABLED`); a signature is refused (`MAINNET_SIGNING_DISABLED`, offline signing included) and so is a broadcast (`MAINNET_BROADCAST_DISABLED`), before any connection, signer call or record. Every connection to any node is asked its identity once before anything else, and a node that answers mainnet is closed and refused. Right before each broadcast, the node is asked again which network it serves (MAINNET-PERIMETER-1), whichever client is used. No signing route of `@hardkas/accounts` signs mainnet either, a direct library call included (HK-12). `allowPublic`, `experimental`, `allowMainnet`, `--allow-mainnet*` and `HARDKAS_*` variables have no effect on any of this.
- **The node has the last word.** Local checks narrow what can go wrong. None of them stands in for the node's own script execution. HardKAS records what the node answered.
- **A fee limit is always in force** for planned payments (TX-05). It is the plan's `maxFeeSompi`, or the workspace's `networks[<net>].maxFeeSompi`, whichever is lower. Without either, the default is 10,000,000 sompi (0.1 KAS), the minimum relay fee of a maximum-mass standard transaction. A node's fee-rate estimate above `networks[<net>].maxFeeRate` (default 10,000 sompi/gram) is refused (`FEE_RATE_ABOVE_BOUND`).

PSKT sessions do not broadcast through HardKAS. Their native signer (`pskt.registerNativeAdapter()`, experimental) refuses before signing anything when any of these fails:

- every input declares SIGHASH_ALL (`PSKT_SIGHASH_NOT_ALLOWED`);
- each signed input's UTXO script is the key's own P2PK (`PRIVATE_KEY_DOES_NOT_CONTROL_INPUT`, decided by the script, not by the PSKT's `bip32Derivations`);
- the session's network is known (`PSKT_NETWORK_REQUIRED`) and is not mainnet.

## Notes

1. **Before the default payment send**, the inputs are checked twice, earlier in the flow:
   - At plan time, against the node's UTXOs and mempool. Covenant UTXOs are left out, and so are outpoints a mempool transaction is spending and immature coinbases. Consolidations leave out immature coinbases too (HK-10).
   - At sign time, `tx.sign` asks the node about each input. It refuses a covenant UTXO, or an input the node does not list.

   A signed artifact that was made elsewhere, or that sat waiting, is not checked again before the default send. The preflight closes that gap, and only when the caller asks for it.
2. **What the preflight verifies, and how far it goes.**
   - It rebuilds the transaction exactly as the client sends it (official kaspa-wasm), with the node's UTXO entries. It verifies each signature against those entries.
   - Anything it cannot verify refuses the send: a P2SH or ECDSA input, another sighash type, another unlock form.
   - It is one node's view at one instant (scope `observer-local`). An outpoint missing from that node's mempool may still be spent elsewhere on the network.
   - It is not available on the simulator, and not for v1 engine transactions, which run their own check.
3. **"Recorded once, never sent again"** applies to an outcome HardKAS cannot know: a timeout, a lost connection, an "already in the mempool" answer. The transaction is observed (`hardkas tx status`, `hardkas tx wait`), not sent again. A request that never left the process is not a submission, and can be sent.
4. **The dev-server** is a local tool.
   - Escrow records are journaled to `.hardkas/escrow-store.json` in the workspace, or `HARDKAS_ESCROW_STORE_PATH`. They survive a restart. Their protection is the workspace's file permissions.
   - "confirmed" means a chain block of the node accepted the transaction, as the SDK's observer reads it from the virtual chain. The node has no transaction lookup by id.
   - The dev-server signs with its own accounts for an HTTP client (`POST /api/tx/send` with `allowDevAutoSign`, `POST /api/tx/sign`) only where the server decides (TX-06). It is off by default: only the server's environment opens it, with `HARDKAS_DEV_SERVER_AUTOSIGN=1`, and then only on the simulated ledger or a local simnet (its declared network is simnet and its node endpoint is loopback). Testnet, devnet and mainnet, in any spelling or through a config alias, are refused (`DEV_AUTOSIGN_NOT_ALLOWED`) before anything is planned, signed or sent. The client's `allowDevAutoSign: true` is required on the send, but never enough by itself.
5. **Signed transactions without a plan** (HK-11). A transaction signed outside this workspace's plan → sign flow names no plan: its lineage has no `parentArtifactId`. HardKAS can neither compare it with a plan nor derive its fee, so the default send refuses it (SEND_PLAN_UNRESOLVED). With `tx.send(signed, { allowUnplannedSignedTransaction: true })` (CLI `hardkas tx send <file> --allow-unplanned`), it is sent without those two checks. The caller takes both on, and the submission records `fee: insufficient-evidence`. The exception never covers:
   - a parent that is named but absent;
   - a parent that is not a plan;
   - a v1 transaction;
   - the preflight, which needs the plan.
6. **A payment this workspace has no record of** (sent from another workspace, or its record lost; TX-SEND-IDEMPOTENT-2 and -3, INT9 · I-2). Before the broadcast, under the transaction's lock, the default send asks the node, read-only, for **positive** evidence that it already has the transaction, in this order:
   1. its mempool holds the txId → `ALREADY_SUBMITTED`, state `MEMPOOL`;
   2. this workspace stores looks at the txId (from `tx status` / `tx wait`): one more look from them, not stored, accepts it → state `ACCEPTED`, `CONFIRMED` or `FINALIZED`, with the accepting chain block and its blue-score confirmations (also when the mempool still lists it: a node can keep an entry its chain already accepted, rusty-kaspa #1146, and the chain's answer wins);
   3. an output of this txId is listed at the address it pays, with the amount and script the transaction gives it (the txId commits to its outputs, so the node's UTXO index lists such an entry only once its virtual chain accepted the transaction) → state `IN_CHAIN`, with the output and the DAA score it was accepted at. Blue-score confirmations are not measured by this read: `hardkas tx status <txId> --since <chain block>` measures them.

   Each of those refuses the send with its evidence. Nothing is sent or recorded, and `hardkas tx send --json` answers `outcome: "already-submitted"`, `code: "ALREADY_SUBMITTED"`, `state`, `evidence`, `recorded: false`, exit 0.

   **Nothing is ever concluded from what the node does not list.** "Inputs not listed" never means "already confirmed": the UTXO index lags behind the chain and the mempool (TX-BATCH-1, TX-WAIT-CHAINED-SPEND-1), and an output may have been spent since. So:
   - nothing found, every read answered → `NOT_OBSERVED`: the broadcast goes ahead and the node judges. If the transaction was in fact already in the chain with all its outputs spent, rusty-kaspa 2.1.0 answers "transaction … was already accepted by the consensus" (seen on simnet when the same transaction was handed to the node again). HardKAS records that answer once as an unknown outcome, not a rejection (P0-TX-SAFETY-1A), and never sends it again: `tx status` / `tx wait` decide its state;
   - a read the node could not answer (no UTXO index, a lost connection, an index entry under this txId with another amount or script) → `UNKNOWN`: **the broadcast goes ahead too**. The node that cannot answer the reads either answers the submit, and its answer is recorded, or does not, and the outcome is recorded as unknown (note 3). Refusing instead would block every send to a node without a UTXO index;
   - the send result names the check (`nodeCheck`: its state and each read); the CLI prints it under `nodeCheck` with `--json`.

   With `--preflight`, an input the node no longer lists, created by no transaction in its mempool, with no output of this transaction listed, refuses the send with `INPUTS_SPENT_UNATTRIBUTED` (it was `INPUTS_SPENT`): nothing proves who spent it — another transaction, this one with its outputs spent since, or an index that has not applied its creator yet. An input whose creator is still in the mempool keeps the preflight's `INPUT_NOT_UNSPENT`. v1 engine transactions are not broadcast in that case either: their own check (F1.6) refuses an input the node does not list.

   Evidence: SDK `tx-send-idempotent-2` and `-3` (stand-in node); the CLI against a real rusty-kaspad 2.1.0 on simnet (`cli-lifecycle.simnet`: a CONFIRMED payment whose submission record was deleted is not sent again, counted at the wire). No testnet-10 evidence.
7. **The node must say it is synced, from the SDK too** (RC1 · D3, Breaking for the SDK). The CLI's `tx send` always used a client that refuses, at connection, a node that does not say it is synced. The SDK's `tx.send` did not: it sent to whatever node its client reached. Now every real `tx.send` (and so `covenants.send`, `accounts` sends and workflow sends, which go through it) asks the node, before any read the send depends on and before anything is sent or recorded (`getServerInfo`). Only `isSynced: true` lets it go on; `false`, a missing or non-boolean value, a client with no `getServerInfo` or a failed read are `NODE_NOT_SYNCED` (a `NodeSyncError`, the same type the CLI's client raises). A connection failure while asking stays `RPC_CONNECTION_FAILED`. This matters: rusty-kaspad v2.1.0 itself **accepts** a `submitTransaction` while it says `isSynced: false` (probed on simnet), so the refusal is HardKAS's.
   - The one exception is explicit and local: `tx.send(signed, { allowUnsyncedNode: true })`, for a controlled simnet or devnet (a node with no peers that has not mined a recent block). It must be a boolean (`SEND_OPTION_INVALID`), it is refused on every other network, testnet included (`SEND_UNSYNCED_NODE_NOT_ALLOWED`), and no other option implies it. Mainnet stays refused before it is read. The CLI has no such option.
   - Network identity, sync, mempool and confirmation stay separate verdicts: a synced node is not a confirmation.
   - Not covered yet: the **Toolkit wallet** route (`WalletToolkit`, also opened as `sdk.wallet.open`, a simnet-only development facade) submits without asking for sync. The check it would use is exported (`assertBroadcastNodeSynced` of `@hardkas/kaspa-rpc`); adding it changes the order of the node reads its P0-TX-SAFETY-1B tests pin, so it is left open for the owner.
   - Evidence: SDK `send-synced-node-rc1-d3` (stand-in nodes that lie about sync); a real rusty-kaspad 2.1.0 on simnet (`send-sync-v0-mass-rc1.simnet`): a fresh node, kept unsynced while old-timestamp blocks mature its coinbases, gets no `submitTransaction` (counted at the wire) and the payment is `NODE_NOT_SYNCED`; another payment sent with `allowUnsyncedNode` is accepted by that node; after one block with a current timestamp the node says it is synced and the refused payment goes out once.
8. **Waiting for a payment sent elsewhere** (`tx wait --address`, RC1 · D2). A transaction accepted before the wait started is looked for by a bounded walk back along the node's selected chain (`--lookback`, default 1000 chain blocks, at most 10000), and its acceptance is the node's own virtual-chain answer from the block it reached; past the bound the wait ends with `TX_WAIT_ACCEPTED_BEFORE_CURSOR` and claims nothing. A mempool entry is never a confirmation. Details: `docs/status/limitations.md`, "Waiting for a transaction sent outside the workspace".

L2 (Igra) sends are not covered here.
